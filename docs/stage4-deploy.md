# 第4段: 配備条件と計測（ADR 0068 決定 4〜7、Issue #7）

固定版: Sigil `1a4bf74c09ff5e83d7bb7a5426e3e50095495568`（単調時計 API を含む）、
shield-tls `63d3051b18e6d0e90c1ebe8f76e6ce267d7534a4`、
Argus `113aeed4932d841d752d752e77dc767ed6b4c886`。

## 1. 制限値と既定値（決定 6）

範囲外・非数値の値は起動時に拒否します（標準出力に `1` を出して終了）。再読込は
プロセスの再起動で行うため、再起動時に同じ検証が働きます。

| 環境変数 | 既定 | 受理範囲 | 意味 |
|---|---|---|---|
| （固定） | 8 KiB | — | 要求行。超過は 414 |
| （固定） | 16 KiB / 100 件 | — | ヘッダー合計と件数。超過は 431 |
| `AEGIS_UPSTREAM_BODY_LIMIT` | 1048576 | 1〜1048576 | 本文。上流の上限が小さければそちらが勝つ。超過は 413 |
| `AEGIS_DEADLINE_MS` | 10 | 1〜10 | 検査の絶対期限。超過は 503 |
| `AEGIS_MAX_CONNECTIONS` | 64 | 1〜256 | 同時接続（上限で受付を止める） |
| `AEGIS_RECEIVE_TIMEOUT_MS` | 30000 | 100〜60000 | 受信期限。超過は 408 |
| `AEGIS_UPSTREAM_CONNECT_TIMEOUT_MS` | 10000 | 100〜60000 | 上流接続期限 |
| `AEGIS_UPSTREAM_RELAY_TIMEOUT_MS` | 30000 | 100〜120000 | 上流応答期限 |
| `AEGIS_NODE_RATE` / `AEGIS_NODE_BURST` | 300 / 600 | 1〜1000000 | 全体のレート（毎秒／瞬間） |
| `AEGIS_KEY_RATE` / `AEGIS_KEY_BURST` | 20 / 40 | 1〜1000000 | 送信元ごとのレート |
| `AEGIS_RATE_TABLE` | 256 | 1〜4096 | 追跡する送信元の最大数 |

ルール数（上限 `max_rules`）、入力長、評価ステップ（`max_search_steps` 100,000）、
送信待ち件数も有限です。400 は曖昧なフレーミング（Content-Length と
Transfer-Encoding の併用、重複 Content-Length 等）です。検査未了の要求は転送せず、
同じ制限は `log_only` の設定にも適用されます。

429 は `Retry-After`（秒、算出できるとき）を付け、新しい送信元で表が満杯のときは
既存の鍵を追い出さずに 503 を返します。レート判定は本文の検査より前です。

## 2. 期限の扱い

期限は `clock.monotonic_nanos()` で、検査開始時、4 ルールごとの作業単位の境界、
転送直前に確かめます。単位の途中で強制中断する保証はありません（超過は次の確認点で
検知されます）。時計が読めないときは期限切れ扱いで 503 です。

## 3. メモリ上限

同時接続 N の最悪値は `N × (16 KiB + 2 × 本文上限 + 128 KiB)` です（要求のバイト列と
転送用の写しを保持するため）。既定では 64 × (16 KiB + 2 MiB + 128 KiB) ≒ 137 MiB。
実測（1 MiB 本文を 64 並列）の最大常駐は約 122 MiB でした
（`docs/measurements/stage4-memory.jsonl`）。上限を下げたいときは
`AEGIS_MAX_CONNECTIONS` か `AEGIS_UPSTREAM_BODY_LIMIT` を下げます。

## 4. 計測記録

- 機器: Intel Xeon @ 2.10GHz、4 論理 CPU、メモリ 15.7 GiB、Linux 6.18、Python 3.13。
- ルール版: 既定の管理ルール（10 ルール）。送信元は固定の PROXY v2、上流はループバック。
- 対象: 364〜884 バイトの代表要求 8 種（1 KiB 以下）、各 1500 件、計測日 2026-11-28。
- 値は `waf_decision_seconds` のヒストグラム（上限境界ごとの割合）から求めます。

| 同時数 | 平均 (ms) | 2 ms 以内の割合 | p95 の上界 | 備考 |
|---|---|---|---|---|
| 1 | 0.65 | 96.9% | 2 ms | **基準（p95 ≤ 2 ms）を満たす** |
| 2 | 1.95 | 53.7% | 5 ms | 満たさない |
| 4 | 3.75 | 1.4% | 5 ms | 満たさない（503 が 2 件） |
| 8 | 3.91 | 1.1% | 10 ms | 満たさない |

**結論**: 追加検査時間 p95 ≤ 2 ms は同時数 1 でのみ確認できました。同時数 2 以上では
検査の実時間が伸びます。Sigil の実行系が実行時呼び出しを直列化していることが疑われ
（原因は未確定）、本リポジトリ側では解消できません。配備は 1 インスタンスあたり
低い同時数（もしくは複数プロセス）を前提にします。この点は Issue #7 に報告済みです。

境界近傍の通常入力（`docs/measurements/stage4-limits-c1.json`、同時数 1、各 40 件、
平均 ms）: 本文 64 KiB 0.65、ヘッダー 16 KiB 2.41、100 ヘッダー 4.18、
本文 1 MiB 4.06、要求行 8 KiB 6.03。8 KiB 要求行と 100 ヘッダーは 10 ms 期限に近く、
一部が 503 になります（同時数 8 では多くが 503、`stage4-limits-c8.json`）。
503 は未検査の要求を転送しない安全側の結果です。

## 5. 誤検知の対応手順

1. 利用者の報告から要求の経路 ID とルール ID（`waf_detections_total` と拒否イベント）を特定する。
2. 当該ルールを `log_only` に変えた版付きポリシーを作り、起動前に `parse_policy` 相当の
   検証（`scripts/check.sh` の試験）を通す。
3. プロセスを再起動して適用し、`waf_detections_total` で影響範囲を確認する。
4. 恒久対応はルールの条件修正として版を上げ、試験を追加する。例外のための迂回は作らない。

## 6. ポリシーのロールバック

ポリシー・CIDR 表・経路表は版付きです。直前の版の設定ファイルへ戻して再起動します。
読み込み失敗や範囲外の値では起動せず（`1` を出力）、半端な設定で動くことはありません。
ロールバック後は `waf_requests_total` と拒否割合が直前の水準に戻ることを確認します。

## 7. 既知の制約

- p95 基準は同時数 1 のみ確認（上記）。同時数が増えると期限超過の 503 が増える。
- レート表の走査は表の容量に比例する（1024 件で新しい鍵 約 2.3 ms、既知の鍵 約 2.4 ms）。
  既定の表を 256 にしているのはこのため。
- 期限は確認点でのみ検知し、強制中断はしない。
- 検証済みの要求ヘッドを公開するパーサー API が無く、検査は再構築した要求を使う。
- 評価系では単調時計を注入できず、期限切れの試験は開始時刻の注入で行う。
- `console.error` が無いため、起動失敗は標準エラーではなく終了時の `1` で示す。
- ルールはデコード前の値と照合する（%エンコード等の正規化は未対応）。
- ヒストグラムの `le` は秒の十進表記（0.0001 など）。
